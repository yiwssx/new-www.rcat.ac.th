## Task-specific acceptance boundaries

### Task 1 — Content Integrity v2: Core Rules

At minimum, evaluate and test semantic checks for:

- duplicate/ambiguous content slug conditions;
- published content with invalid/future publication semantics contrary to the current Worker authority contract;
- malformed Facebook Embed source/permalink state;
- required-field consistency for publishable content;
- invalid or contradictory scheduled-content state;
- invalid media/document/content references where the repository can verify them safely;
- structural menu/content relationship issues without treating intentional navigation placeholders as defects.

Rules must be deterministic and suitable for read-only auditing.

### Task 2 — Production Audit Integration

- Reuse existing production-data operation/audit infrastructure where practical.
- Prefer read-only checks and fail-closed reporting.
- Do not print sensitive URL values, credentials, bookmarks, database IDs, or secret-bearing payloads into CI logs.
- Do not auto-repair production data as part of the audit.
- Avoid a new permanent workflow when an existing protected/manual production-data operation can own the check.

### Task 3 — Revision History: D1 Schema

The design should support:

- immutable revision rows;
- content identifier and monotonic revision identity/number;
- action type (for example create/update/publish/unpublish/restore);
- actor identity/audit attribution consistent with the existing authenticated Worker boundary;
- complete or intentionally scoped editable-content snapshots sufficient for restoration;
- creation timestamp;
- indexes needed by content-id/history queries;
- additive migration and migration-sequence validation.

No production migration is applied while this workstream is on the integration branch.

### Task 4 — Revision History: Write Boundary

- Revision recording belongs at the authoritative Worker/admin-write boundary, not only in the browser.
- A successful content mutation must not silently skip required revision evidence.
- Avoid partial states between content mutation and revision recording; use D1 transaction/batch semantics supported by the current repository architecture.
- Preserve existing publish-time authority and scheduling semantics.

### Task 5 — Revision History: Admin Viewer

- Read-only revision list/detail UI first.
- Show useful operator information such as revision/action/time/actor without exposing internal identifiers unnecessarily.
- Preserve existing Admin UX/design-system boundaries and current MUI/Tailwind cascade contract.
- Keep Admin responses `no-store` and within existing authentication/authorization boundaries.

### Task 6 — Revision History: Restore

- Restore must create a **new revision** from an older snapshot.
- Never delete or overwrite the historical revision being restored.
- Require an explicit capability/authorization path.
- Reuse existing audit/request-correlation/session assurance mechanisms instead of introducing a parallel security model.
- If product policy is genuinely ambiguous (for example, which roles may restore or when step-up is mandatory), stop for user decision rather than inventing policy.

### Task 7 — Shared Validation Contracts: URL/Link

- Eliminate avoidable duplicate pure validation logic between frontend and Worker.
- Keep client-side validation for UX and Worker-side enforcement for integrity/security.
- Preserve supported Facebook post/Reel/permalink formats and intentional navigation placeholders.
- Do not mix SEO canonical redesign into this task.

### Task 8 — Shared Validation Contracts: Content State/Date

- Keep Worker/server time authoritative for direct publication.
- Preserve valid historical backdating behavior already accepted by the current contract.
- Preserve scheduling rules that require valid future schedule times.
- Consolidate pure transition/normalization logic without making browser input authoritative.
- Add regression tests for the state/date matrix before replacing duplicated logic.

### Task 9 — Release Baseline: v3.3.1

Complete only after Tasks 1–8 are `COMPLETE` and integration regression has passed.

Expected release-baseline work:

- update `package.json` version from `3.3.0` to `3.3.1`;
- reconcile `CHANGELOG.md` with all completed post-3.3.0 production work relevant to this patch baseline, including this workstream;
- ensure release/version consistency governance passes;
- prepare release notes/evidence references;
- do **not** create the `v3.3.1` tag until after the final merge, required production release, and production verification succeed.

## Integration and verification strategy

Because repository CI and Vercel deployment behavior are intentionally centered on `main`, integration-branch verification must be explicit.

During task development:

1. Create a task branch from the current integration head.
2. Implement only that task's scope.
3. Run focused tests and repository-wide checks appropriate to the changed surface.
4. PR the task branch into `integration/v3.3.1-content-ops`.
5. Record branch/PR/SHA/test evidence in this tracker.
6. Advance the integration branch only after the task is verified.

Before final merge to `main`:

1. Confirm all nine rows are `COMPLETE`.
2. Confirm no temporary integration-only CI/Vercel configuration remains unintentionally.
3. Run full integration regression equivalent to the protected release-quality surface, including formatting, lint, unit, integration, build, Worker typecheck/dry deploy, governance, and functional E2E.
4. Review migration sequencing and confirm production D1 has not been mutated during development.
5. Open one final PR from `integration/v3.3.1-content-ops` to `main`.
6. Allow the protected `quality` gate to run on the final PR; do not bypass it.

## Production release sequence after final merge

Only after the final integration-to-main PR has merged and `main` CI is successful:

1. Run the protected Worker production **preflight** on `main`.
2. Resolve exact production D1 identity and pending migrations using the existing release workflow.
3. User/operator manually approves the protected `production` Environment when GitHub requests approval.
4. Run the Worker production **release** from `main`; this is the point at which approved pending D1 migration(s) and Worker runtime changes may reach production.
5. Run/observe the repository's production verification and confirm the exact final `main` SHA is healthy.
6. Only then create/publish the `v3.3.1` tag/release.

Do not expose Time Travel bookmark values, production database IDs, API tokens, or other protected credentials in tracker updates or release notes.

## Manual user/operator actions expected

The user should not need to manually merge the nine task PRs, run tests locally, apply D1 migrations from a shell, or edit production data.

Manual intervention is expected only where the repository intentionally requires human authority:

1. **Production Environment approval** for the protected Worker production release after the final merge.
2. **Product-policy decisions** only if implementation reaches a genuinely ambiguous policy boundary (for example revision-restore role/capability or mandatory step-up policy) that cannot be derived safely from existing repository contracts.
3. Any external-provider/account action that cannot be performed by the connected tooling and is explicitly required by the final validated design.
