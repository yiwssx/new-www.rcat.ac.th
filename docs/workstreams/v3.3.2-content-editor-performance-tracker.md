## Objective

Reduce the Admin content editor JavaScript cost without changing editor behavior, saved content shape, Worker/API contracts, D1 schema, or public-site performance architecture. The workstream must reduce real bytes and isolate editor-only dependencies; it must not hide the problem by raising Vite chunk warning limits.

## Baseline

Production build evidence before this workstream:

| Asset                                 |       Raw |      Gzip |
| ------------------------------------- | --------: | --------: |
| `ContentEditorDialog`                 | 499.31 kB | 153.24 kB |
| application `index`                   | 375.60 kB | 118.65 kB |
| `PreviewRevisionAutosaveWorkflowPage` | 170.63 kB |  44.35 kB |

Current editor dependency chain:

`ContentPage` → lazy `ContentEditorDialog` → static `ContentBlockBuilder` → static `RichTextEditor` → Tiptap/ProseMirror + editor extensions + media-picker UI.

`/admin/content` already lazy-loads `ContentEditorDialog`; the optimization target is the graph behind that boundary, not the public synchronous graph.

## Release invariants

- Do not change the public content format or `RCAT_BLOCKS_V1` compatibility.
- Do not change CMS Worker/API payload contracts.
- Do not add, alter, or apply D1 migrations.
- Do not deploy the production Worker or Apps Script for this workstream.
- Do not raise `chunkSizeWarningLimit` to hide bundle growth.
- Do not use `manualChunks` as the only claimed optimization when transferred bytes remain materially unchanged.
- Preserve create/edit/save, rich-text formatting, table, link, media insertion, draft recovery, and session-expiry behavior.
- Keep Tiptap/ProseMirror out of the public synchronous graph and out of the initial `/admin/content` list graph.
- Temporary CI support for the integration branch must be removed in Task 9 before final integration to `main`.

## Release targets

These targets are architectural release gates, not a substitute for field measurements:

- no single editor-specific emitted JavaScript chunk at or above 400 kB raw;
- preferred largest editor-specific chunk below 350 kB raw where achievable without behavior loss;
- aggregate first-editor-open gzip bytes must not exceed the 153.24 kB baseline;
- target at least 10% aggregate first-editor-open gzip reduction (approximately 138 kB or lower);
- no Tiptap/ProseMirror modules in the public synchronous graph;
- no Tiptap/ProseMirror modules in the initial `/admin/content` list graph.

Any release-target adjustment requires measured build evidence and an explicit architecture rationale; thresholds must not be raised merely to make CI green.

## Execution model

Each Task branch is created from the latest verified integration-branch head only after the preceding Task has merged. Every Task PR targets `integration/v3.3.2-content-editor-performance`. Final integration to `main` happens only after Tasks 1–9 are complete and temporary integration-only CI support has been removed.

## Production sequence

This workstream has no D1 or Worker production mutation. After final integration to `main`:

1. allow the normal Vercel production deployment from `main`;
2. require the existing Production Verification path to pass for the exact release commit;
3. perform non-mutating Admin editor smoke checks: `/admin/content`, create/edit dialog load, rich-text toolbar availability, and media-picker load without chunk/module errors;
4. create tag `v3.3.2` and GitHub Release only after verification passes;
5. perform a separate reconciliation PR to close the tracker and align canonical project/release state.

## Safety / interruption rule

Do not skip ahead by merging an unverified Task into integration. If a Task exposes a regression, fix that Task branch or supersede it with a clean reconstruction from the latest verified integration head. Do not use production mutation or deployment as a debugging mechanism.
